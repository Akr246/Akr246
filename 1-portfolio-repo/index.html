SpendLens

Behavioural spend-intelligence web app · concept to live build
PRODUCT SPECREACT / TYPESCRIPTDECISION ENGINESSHIPPED

Most money apps tell you what you spent. This one classifies every rupee as essential or flexible, then gives an honest verdict on whether a stated financial goal is reachable — and three trade-offs drawn from the user's own spending when it isn't.

What I did

Wrote the requirements, defined the four-band classification model and the success metrics, then shipped it as a React and TypeScript application deployed through GitHub Actions using AI-assisted development. The PRD covers scope, metrics, competitive position, and the published research that argues against the product's own thesis.

Two decisions worth defending

Classification carries a confidence score. Anything below the threshold goes to a human review queue instead of rendering. A confident wrong answer costs more trust than an honest question, and unlike a missing answer you don't recover from it.

A guardrail service sits between the engines and the interface. It blocks any recommendation touching an essential expense and can overrule every layer beneath it — deliberately separate code, because a guardrail that lives inside the thing it guards isn't a guardrail.

Why React and TypeScript

One constraint decided it: the product invites you to import a real bank statement, so nothing can leave the device. That ruled out any architecture with a server. TypeScript because the classification logic has four bands, six engines and heavy branching. Charts are hand-rolled SVG so a forecast can be drawn as a confidence band rather than a single line.

What I'd change

The research I found while writing the PRD says category-split budgets and precise figures both increase spending. The current build does both. That's the first thing to fix, and finding it was more useful than any feature I could have added.

How I tend to work

  • Write the spec before the ticket.Most disagreements are far cheaper to have on paper than in week three of a sprint.
  • Attach a number to the outcome.And say plainly when there isn't one, rather than reaching for a proxy that flatters.
  • Design for the case where the system doesn't know.That's usually where trust is won or lost, and it's the part that gets left out of the diagram.
  • Include what argues against you.A document that carries only supporting evidence isn't analysis, and the reader can tell.
